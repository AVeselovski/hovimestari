**The problem, stripped of the proposed mechanism:** a person can create an account, get in by password or Google, stay in on a phone, recover a forgotten password, manage how they sign in and delete everything, inside an installable app shell that later steps fill. The proposed mechanism, lifting finanssi, is accepted with one change: finanssi's browser session hands the refresh token to JavaScript in three places, which NFR-SEC-03 forbids. The fix reuses finanssi's own route-handler pattern rather than adding machinery (decision 3). The proposed slicing into two PRs is changed to three (section j), because the overlay primitives are a large, separately reviewable body of lifted code whose first consumer is the account section.

**Login CSRF and a hijacked Google finish** (review) are closed by a same-origin guard on every state-changing route handler and a browser-bound nonce on Google sign-in (sections d and e). Neither is left as a residual risk.

**Changes proposed that were not asked for** (each repeated in section h):

1. Error responses carry a stable `code` beside `message`, and the web app renders catalog copy by code.
2. A database CHECK that a user always has a password or a Google id.
3. A CI step that fails when the Drizzle schema and the committed migrations disagree.
4. A root `pnpm env:init` script that writes local `.env` files with generated secrets.
5. The four macro hues reserved now (0.7).

**Requirements drift:** none. `docs/requirements.md` and `docs/overview.md` match this plan.

## a) Overview

Step 1 deletes the earlier app, parks what later steps salvage, and lays the new monorepo: `apps/backend` (Express 5, Drizzle on Postgres 16), `apps/web` (Next.js 16 App Router, installable as a PWA) and `packages/types` (Zod 4 schemas shared by both), on Turborepo, Jest, ESLint and the `next-intl` catalog. Authentication is lifted from finanssi and trimmed to one user per account: no vaults, members, invitations, Drive, tax or recurring stubs. Its browser session changes so that no refresh token ever reaches JavaScript. The signed-in shell is four tabs with a bottom tab bar on a phone and a side rail from `md` up, in the Nordic kitchen-counter identity in light and dark. It ships empty, so steps 2 and later add screens into it without touching its frame. It lands in three pull requests, each leaving `master` green.

## c) Data model

Three tables. One migration, `0000_auth.sql`, generated by `drizzle-kit generate` into `apps/backend/drizzle/migrations/`. Nothing to migrate from: the earlier app's database is a different database (section g, decision 12).

```ts
// apps/backend/src/db/schema/users.ts
import { sql } from "drizzle-orm";
import { check, pgTable, text, timestamp, uuid } from "drizzle-orm/pg-core";

export const users = pgTable(
  "users",
  {
    id: uuid("id").primaryKey().defaultRandom(),
    // Always stored trimmed and lower-cased: the Zod schema normalises before any query.
    email: text("email").notNull().unique(),
    passwordHash: text("password_hash"), // null on a Google-only account
    googleId: text("google_id").unique(), // null on a password-only account
    createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [
    // FR-AUTH-05: an account always keeps a way in.
    check("users_has_sign_in_method", sql`${t.passwordHash} IS NOT NULL OR ${t.googleId} IS NOT NULL`),
    // Stored lower-case; this makes a mixed-case write fail loudly instead of creating a twin.
    check("users_email_lower", sql`${t.email} = lower(${t.email})`),
  ],
);
```

Rules the code carries:

- **One session per row.** Rotation deletes the used row, sweeps the user's expired rows and inserts the new one in one transaction, as finanssi's `issueTokens`.
- **Reset tokens.** Redeeming one deletes every reset token of that user, not only the one used, then sets the password and calls `endAllSessions`. Expired rows go on first use, as finanssi.
- **Passwords.** 8 to 72 UTF-8 bytes, checked in the Zod schema with a byte-length refine. bcrypt cost 12.
- **The cascade rule, binding every later step.** Every table that holds a user's data has `user_id uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE`, or reaches `users` through a chain of cascading foreign keys. `src/db/__tests__/userCascade.db.test.ts` proves it two ways on a fully migrated throwaway database (review):
  - **The graph walk.** Starting from `users`, it follows `pg_constraint` foreign keys backwards to every table that references a table already reached, until nothing new is reached. Every edge into that reachable set must have `confdeltype = 'c'`. A child table that points at a user-owned parent with `SET NULL`, `RESTRICT` or `NO ACTION` (recipe ingredients pointing at recipes, say) fails, because it would leave orphans or block the deletion. A table with a `user_id` column outside the reachable set fails too.
  - **The deletion.** `seedOneOfEach(db, userId)` in `src/db/__tests__/support/seedOneOfEach.ts` inserts one row into every user-owned table for each of two users. The test deletes one user and asserts zero rows of that user remain in every table, and the other user's rows are all still there. The test also fails when the graph walk reaches a table that `seedOneOfEach` does not seed, so a step cannot add a table and forget the check. In step 1 it seeds `refresh_tokens` and `password_reset_tokens`.

  Tables shared by every user (Fineli foods in step 2) are not reachable from `users` and are untouched by a deletion. A shared table that a user's row points at is fine: the edge goes the other way.

**Migration workflow.** Change `src/db/schema/*.ts`, run `pnpm --filter @hovimestari/backend db:generate`, commit the SQL and the `meta/` snapshot together. Locally `db:migrate` applies them. Fly runs the lifted `release_command`. Tests apply them with `drizzle-orm/node-postgres/migrator` on a throwaway database. CI runs `db:generate` and then fails when `git status --porcelain apps/backend/drizzle` prints anything, so a schema change without its migration fails. `git status`, not `git diff`, because a missing migration shows up as a new, untracked file (review). Rollback is forward-only, as in finanssi: a bad migration is reverted by a new one.

## d) API interface

**From a Zod issue to a code** (review). The body parser takes the first issue. When its message is a member of `ERROR_CODES`, that is the response's `code`, and `message` is the backend's fixed English text for the code (`ERROR_MESSAGES` in `src/lib/errors.ts`, for API clients and logs). Any other issue answers 400 with `code: "invalid_request"` and `message: "The request is not valid."`, never the raw Zod text.

**Deleting an account, the server rule** (review). When the account has a password (`password_hash` not null), the body must be `{ password }` and the password must match. `{ email }` is accepted only when `password_hash` is null, and must equal the stored email after normalising. **Same-origin guard** (review). `requireSameOrigin(request)` in `_guard.ts` runs first in every route handler that accepts a POST: sign-in, sign-up, refresh and sign-out, and any added later. It answers 403 `request_refused` unless `Sec-Fetch-Site` is `same-origin`, or, when that header is absent, `Origin` equals the request's own origin. A request with neither header is refused. Handlers that read a body also answer 415 `request_refused` unless `Content-Type` is `application/json`, so a cross-site `<form enctype="text/plain">` that happens to carry valid JSON is refused before it is parsed. Together these stop login CSRF: another site cannot sign a visitor into an account it controls and then read what they log (NFR-PRIV-01). Tested in `src/app/api/auth/__tests__/guard.test.ts` for each rule, and in `allHandlersGuarded.test.ts`, which imports every `src/app/api/**/route.ts` that exports `POST` and checks that a request with `Sec-Fetch-Site: cross-site` gets 403 and a same-origin `text/plain` body gets 415 from each. A new handler without the guard fails that test.

**Client address** (review). Every relay call carries `X-Bff-Secret` and `X-Client-Ip`. In production the handler reads only `x-real-ip`, which Vercel sets from the connecting address and a client cannot override. When it is missing the handler answers 500 and relays nothing. `x-forwarded-for` is never read, because outside Vercel's edge a client can set it. In development the handler sends `x-real-ip` when present and `127.0.0.1` otherwise. The backend answers 400 `client_address_missing` to a relayed call without `X-Client-Ip` when `NODE_ENV=production`, and 400 `client_address_invalid` when the header is not an IP address (review 2). The relay secret's real job is to authenticate that header: it is what lets the backend believe an address a request names for itself, and it keeps the refresh token behind the web server.

**Rotating `BFF_SECRET`** (review). The value lives on Fly and on Vercel, which cannot change at the same moment. The backend accepts `BFF_SECRET` and an optional `BFF_SECRET_PREVIOUS`. Rotation: set the new value as `BFF_SECRET` and the old one as `BFF_SECRET_PREVIOUS` on Fly, then change Vercel's value and redeploy the web app, then remove `BFF_SECRET_PREVIOUS`. The Vercel variable is scoped to Production only, so preview deployments never hold it. The Fly and Vercel runbooks carry these steps. The relay helper lives in `src/app/api/auth/_relay.ts` with `BACKEND_URL` and `BFF_SECRET`, which are server-only and never prefixed `NEXT_PUBLIC_`. "Sign out on all devices" is two calls from the browser: `POST /auth/logout-all` with the bearer, then `/api/auth/sign-out`.

## e) Data flow

**Sign up or sign in with a password.**

1. The form parses `RegisterBody` or `LoginBody` client side and shows field lines on failure.
2. `AuthContext.signIn` posts to `/api/auth/sign-in`.
3. The route handler relays to `POST /api/v1/auth/login` with the secret and the client address.
4. The backend: `requireBff`, then the address limiter, then the per-account limiter (both keyed by `clientIp`, which trusts `X-Client-Ip` only beside a valid secret), then bcrypt, then `issueSession` (one transaction: sweep expired rows, insert the new hash), then `{ accessToken, refreshToken, user }`.
5. The route handler sets the cookie and returns `{ accessToken, user }`.
6. `AuthContext` keeps the access token in memory, arms the refresh timer 60 s before expiry, sets `authenticated`. `GuestGuard` sends the user to `?redirect=` or `/`.

**Restoring a session on launch.** `AuthProvider` posts `/api/auth/refresh` once on mount. 200: authenticated. 401: unauthenticated, `AuthGuard` sends the user to `/auth/sign-in`. 503 or a network failure: status `offline`. `AuthGuard` renders the shell, the offline strip shows, and the provider retries on the `online` event and with backoff (2 s, 5 s, 15 s, then 60 s). This replaces finanssi's behaviour, which treats any failed refresh as a sign-out.

**Refresh rotation and concurrency.** Two tabs refreshing with one cookie: the transaction deletes the consumed hash before inserting, so the second refresh finds no row and gets 401. The lifted Axios interceptor already shares one refresh across requests within a tab. Across tabs, the loser signs out. That is finanssi's accepted behaviour, kept.

**Google sign-in.** The flow is bound to the browser twice: the backend's own state cookie ties Google's answer to the browser that went to Google, and the web app's nonce ties the finished sign-in to the browser that started it (review).

1. The sign-in page saves `?redirect=` to `sessionStorage.postLoginRedirect` and navigates to `/api/auth/google/start`. That handler sets the `__google_sign_in` nonce cookie and redirects to `${NEXT_PUBLIC_API_URL}/auth/google?bind=<sha256(nonce)>`.
2. The backend refuses a start without a well-formed `bind` (302 `?error=google_failed`). It signs a `google-sign-in` state carrying `bind` in its fields, sets its own nonce cookie scoped to the callback path, and redirects to Google.
3. Google returns to `/auth/google/callback`. `requireOwnState`, then Passport. Found by Google id: that user. Found by email without a Google id: redirect `?error=google_email_taken`. Not found: create a Google-only user.
4. The callback issues a one-time `google-sign-in` code for the user id and the state's `bind` (60 s, single use, in process) and redirects to `${FRONTEND_URL}/api/auth/google/complete?code=…`. No token is in any URL.
5. The route handler reads the nonce cookie and relays `POST /auth/google/exchange` with `{ code, nonce }`. The backend spends the code, then requires `sha256(nonce)` to equal the code's `bind` (timing-safe). The handler clears the nonce cookie, sets the refresh cookie, and redirects to `/auth/sign-in`. A link an attacker made by finishing their own Google flow fails in the victim's browser, which holds a different nonce or none. Tests: an exchange with another browser's nonce, with no nonce cookie and with a spent code each end on `google_failed` and set no cookie.
6. `AuthProvider` mounts, refreshes, becomes authenticated, and `GuestGuard` forwards to the saved redirect.

**Linking Google** (review 2). Bound to the browser the same way as sign-in. A ticket the attacker made for their own account and sent to a victim who has already consented to Google would otherwise link the victim's Google id to the attacker's account, and the victim's next "Continue with Google" would sign them into it. The backend half lands in PR 1, the web half in PR 3 with the account section.

1. **Link Google account** on Settings posts to `/api/auth/google/link/start` with the bearer. The handler runs the same-origin guard, makes a 32-byte nonce, sets it in the `httpOnly` cookie `__google_link` (`sameSite: "lax"`, `secure` in production, `path: "/api/auth/google/link"`, 10 minutes), and relays `POST /auth/link/google/start` with the bearer and `{ bind: sha256(nonce) }`.
2. The backend refuses when Google is off or already linked, signs a `google-link` state over the user id and `bind`, and answers `{ url }`. The page navigates to that URL. The backend sets no cookie of its own here, because the call is server to server; the web nonce is the browser binding.
3. Google returns to `/auth/link/google/callback`. It verifies the state's signature, purpose and expiry, lets Passport exchange Google's code for the profile, and links nothing. It issues a `google-link` one-time code bound to the user id, the Google id and `bind`, and redirects to `${FRONTEND_URL}/api/auth/google/link/complete?code=…`.
4. `GET /api/auth/google/link/complete` reads the nonce cookie, clears it on every outcome, and relays `POST /auth/link/google/exchange` with `{ code, nonce }`. The backend spends the code, requires `sha256(nonce)` to equal its `bind` (timing-safe), refuses a Google id another user holds (`google_taken`), and only then sets `google_id` on the code's user. The handler redirects to `/settings?google=linked`, `taken` or `failed`.
5. The settings page shows the result line, invalidates `me`, and removes the parameter with `router.replace`.

The two `complete` handlers are GET navigations that arrive from Google through the backend, a cross-site chain, so the same-origin guard cannot apply to them. The nonce is what protects them. Tests, equal to the sign-in ones: an exchange with another browser's nonce, with no nonce cookie, and with a spent code each end on `failed` and link nothing; a code for a Google id another user holds ends on `taken`; the start handler refuses a cross-site POST.

**Forgotten password.** `POST /auth/forgot-password` direct from the browser (no token involved, so no relay, and the limiter sees the real address through `Fly-Client-IP`). An account with a password gets a token row and a mail. The page shows the same answer for a 200 and for a 429. `POST /auth/reset-password` sets the password, deletes the user's reset tokens and calls `endAllSessions` in one transaction. The page then sends the user to `/auth/sign-in?reset=1`.

**Change password** (PR 3). `PUT /users/me/password` ends every session in its transaction. The sheet then calls `AuthContext.signIn(email, newPassword)` so this device continues (0.10).

**Delete account** (PR 3). `DELETE /users/me` with the confirmation. One statement, `DELETE FROM users WHERE id = $1`, inside a transaction, and Postgres cascades the rest. The web app then calls `/api/auth/sign-out` (its backend `logout` finds no row and still answers 204), clears the query cache by unmounting `QueryProvider`, and replaces the route with `/auth/sign-in?deleted=1`.

**`endAllSessions(tx, userId)`** in `src/lib/sessions.ts` deletes every refresh row. Step 4 adds connection revocation inside it (FR-AI-15), so password change, reset and every future caller get it at once.

## g) Constraints and decisions

1. **Three pull requests, each green on its own** (section j). Cutting the overlay primitives into their own PR keeps PR 2 about the app's frame, and the primitives land with their first real consumer.
2. **Turborepo**, lifted from finanssi. The root script names stay `build`, `typecheck`, `lint`, `test`, `docs:check`, so CI keeps its steps.
3. **No refresh token reaches browser JavaScript (NFR-SEC-03).** Every backend route that answers with a refresh token requires a relay secret only the web server holds, and the browser talks to those routes only through same-origin route handlers. The relay also forwards the client's address, so the rate limiters keep keying on the real person (FR-AUTH-06), not on the web server. Google sign-in finishes through a one-time code bound to a nonce the starting browser holds, so no token appears in any URL and nobody can finish a flow in someone else's browser. Every state-changing route handler refuses cross-site and non-JSON requests (section d). The relay secret authenticates the forwarded address, and production refuses a relay without one. This keeps finanssi's route-handler pattern and adds four handlers, a guard and one header check.
4. **Next.js 16**, not 15. A new app takes the current major rather than a migration a year from now, and the project skill already describes 16. Turbopack builds remove finanssi's dev-versus-build split. Corrections to `.claude/skills/developing-nextjs/SKILL.md` (PR 2): no Server Actions here (mutations go to the Express API with the in-memory bearer token); signed-in pages are client components and put no user data in server HTML; no Cache Components, `use cache`, `updateTag` or `refresh()`, because TanStack Query owns server state; `proxy.ts` is not used; the React Compiler is off; remove the Convex `Id<'tableName'>` line and the `bun add` line; replace the `bg-linear-to-r` gradient example, since the design forbids gradients; add the monorepo `turbopack.root` rule and the no-`.js`-extension rule; `next-intl` needs `transpilePackages` for Jest.
5. **TypeScript 5.9**, not 7. TypeScript 7 is the native port, and ts-jest, typescript-eslint and the Next plugin are unverified on it here. Upgrading is a `TODO.md` item.
6. **Zod 4 everywhere.** Step 4's MCP SDK needs Zod 4, which is why finanssi carries `zod-v4` as a second copy. Starting on 4 avoids two Zod versions. Lifted schemas change `message:` to `error:` and `error.errors` to `error.issues`.
7. **Jest 29** for both apps, as `CLAUDE.md` states, with `@jest/globals`, `ts-jest` and `jest-environment-jsdom` on 29 (finanssi mixes in `@jest/globals` 30). ESLint 9.39, which `eslint-config-next` 16 and `eslint-plugin-react` support. pnpm 10.33, as finanssi. Node 22.
8. **Base UI pinned to `1.8.0`**, the version finanssi verified every Drawer fact in `mobile-ui-lessons.md` against. 1.9.0 exists. Upgrading is a separate task that re-verifies those facts.
9. **Configuration.** Backend `env.ts`: `DATABASE_URL`, `PORT` (3001), `CORS_ORIGIN`, `FRONTEND_URL`, `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` (each at least 32 characters), `JWT_ACCESS_EXPIRES_IN` (`15m`), `JWT_REFRESH_EXPIRES_IN` (`7d`), `BFF_SECRET` (at least 32), optional `BFF_SECRET_PREVIOUS` (during a rotation only), `DB_POOL_MAX` (5), optional `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_CALLBACK_URL`, `GOOGLE_LINK_CALLBACK_URL` (all four or none), optional `RESEND_API_KEY` (required when `NODE_ENV=production`) and `EMAIL_FROM` (required with the key). Web: `NEXT_PUBLIC_API_URL` (with `/api/v1`), `BACKEND_URL` and `BFF_SECRET` (server only, Vercel Production scope only).
10. **Tests and the database, with no Docker and no committed secret.**
    - Every backend suite gets its environment from `src/__tests__/env-setup.ts`: fixed, non-secret values (`NODE_ENV=test`, URLs, expiries) and **generated** secrets (`JWT_*`, `BFF_SECRET`, and `GOOGLE_CLIENT_SECRET` in the Google suites) from `randomBytes(32).toString("hex")` at start-up. There is no `.env.test.example`, and CI has no "create env file" step.
    - Test passwords are made at run time by `testPassword()` in `src/__tests__/support/credentials.ts` (`` `pw-${randomUUID()}` ``). No test, fixture or doc contains a literal password, key or secret.
    - Route tests lifted from finanssi keep their mocked database.
    - Suites named `*.db.test.ts` run on a real Postgres through `describeWithDb`, which creates a throwaway database per suite from `TEST_DATABASE_URL` (default `postgresql://postgres@localhost:5433/postgres`, no password), migrates it and drops it. When the server is unreachable, it fails under `CI=true` and skips with one loud warning otherwise. How a suite reaches its database (review): the app's `db` and `pool` are built from `DATABASE_URL` when `src/db/index.ts` is first imported, so `describeWithDb` creates the database in `beforeAll`, sets `process.env.DATABASE_URL` to it, and only then does `await import("../../app.js")` (and `../../db/index.js` for direct queries), handing both to the suite. Static imports of the app or the database are not allowed in a `*.db.test.ts` file. Each test file has its own module registry under Jest's ESM mode, so suites never share a pool. `afterAll` ends the pool, then drops the database. Step 1's real-database suites: `authFlow.db.test.ts` (sign up, sign in, rotation, concurrent rotation yields exactly one success, logout, logout-all, reset ends every session, change password, unlink refuses the last method and the CHECK refuses it too, delete cascades, email stored lower-case), `userCascade.db.test.ts` (section c), `throwawayDb.test.ts`.

## Deviations from the design

Recorded by the backend engineer while building PR 1. Each is the smallest sound choice where the design could not be followed as written, or left a detail open.

1. **The verbatim lift commit leaves out eight test files.** finanssi's `lib/__tests__/env.test.ts`, `lastResort.test.ts`, `db/__tests__/index.test.ts`, `middleware/__tests__/error.test.ts`, `routes/__tests__/auth.test.ts`, `authRateLimits.test.ts`, `users.test.ts` and `src/__tests__/auth-schemas.test.ts` hold literal passwords or credential URLs. The secret scan reads every commit of a pull request, so committing them verbatim would fail it even with the tip clean. They arrive already adapted in the "adapt" commit, which a reviewer diffs against finanssi directly.
2. **`turbo.json` passes `TEST_DATABASE_URL` and `CI` through to `test`.** Turborepo 2 runs tasks in strict env mode and drops undeclared variables, so without it CI's real-database suites would never see their URL.
3. **Not lifted: `oauthStateFormat.test.ts`.** It checks a link state in finanssi's format from before the shared OAuth state. Hovimestari never had that format. **`users.test.ts` is replaced** by the real-database `authFlow.db.test.ts`: every case it held was the display name or `PATCH /users/me`, which are gone, and the flows it covered now run on Postgres.
4. **`GET /auth/google` has its own suite, `googleStart.test.ts`.** The callback suite stubs the strategy's OAuth client, which also builds the consent URL.
5. **Mail copy.** The design points at section f for it, and section f has none. The reset mail says what happened, that the link works once for an hour, and that nothing changes if it was not the reader.
6. **`packages/types` builds with `tsconfig.build.json`**, which leaves its tests out of `dist/`, and its Jest config is `jest.config.js`, so the package needs no `ts-node`.
7. **Hardening beyond finanssi.** The first three are covered by tests: Google sign-in refuses an address whose account is linked to a different Google id (finanssi signed in). Redeeming a reset link deletes it with `RETURNING` inside the transaction, so two concurrent uses cannot both set a password. A reset mail that fails to send is logged and answered as usual, because a 500 only for real accounts would tell which addresses exist. Unlink also maps a race that trips the `users_has_sign_in_method` CHECK to `last_sign_in_method`.
8. **Codes the design left open:** the relay secret's 401 answers `request_refused`. A body the JSON parser refuses answers `invalid_request`. The rate limiters' messages are `ERROR_MESSAGES` text, so they cannot drift from the codes.
9. **The salvage also parks `packages/shared/src/llm.ts`**, as `canonicalisation/shared-llm.ts`, because both parked prompts import its recipe draft schema. Every parked file is copied from `1243f1b`, the last commit with the earlier app.
10. **The Fly runbook sets third-party secrets with `flyctl secrets import`** from standard input, so no key lands in shell history. Generated secrets are made inline with `openssl rand -hex 32`, as decision 11 says.
11. **The pool's PgBouncer comment** in `db/index.ts` points at the Fly runbook, which says what to change for Managed Postgres, instead of a `TODO.md` item the design does not list.
12. **Fixes from the first validation and review cycle.** Forgot-password answers before it stores the link and sends the mail, which run in the background with a logged `.catch`, so the timing cannot tell which addresses have an account. Storing a link sweeps the user's expired links. A sign-in with no stored hash compares against a dummy hash made at start-up. Shutdown on SIGTERM and SIGINT closes the server and the pool within ten seconds (`lib/shutdown.ts`). `DELETE /users/me` runs its one statement without a transaction.
13. **Two error codes beyond section d:** `unauthorized`, which `authenticate` now answers on every 401, and `google_email_unverified`. Google sign-in and linking refuse a profile whose email Google has not verified: sign-in redirects to `/auth/sign-in?error=google_email_unverified`, linking to `/settings?google=unverified`. PR 2 gives both codes catalog copy or a `CODES_WITHOUT_COPY` entry, and PR 3 shows the `unverified` link result. **Corrected in fix cycle 2:** only the paths that create an account or match by address check for a verified email. An account already linked to that Google id signs in whatever the address's state, and linking does not check, because it stores only the Google id.
14. **A one-time code is spent by the first exchange whose body is well formed.** A body without a nonce is refused before the code is read, so that code stays live for its minute. The table in section d says "spent whatever the outcome". The feature doc states the narrower rule.
