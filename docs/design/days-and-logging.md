## a) Overview

Step 3 turns the Day tab into a food log with a plan under it. An entry is a food by weight, a saved meal by count or an estimate, planned or eaten, on any date. Every entry keeps the values it was added with, so a past day never changes. One read service answers a day's two readings, eaten and with plan, with each range's position and distance, and the week view reads the same service over seven dates. The gauge draws both readings against the calorie and protein ranges on a fixed scale, in the reserved macro hues, with no verdict. The food sheet from step 2 becomes the log sheet: create actions on top, recent items, favourites and saved meals before typing, a "+" that logs a recent item with its last amount in one tap, an amount view in grams or portions with the figures before Log, saved meals with their source tag, and estimates. Every quick action offers Undo in a toast.

### Saved meals

```ts
// apps/backend/src/db/schema/savedMeals.ts
export const savedMeals = pgTable(
  "saved_meals",
  {
    // The web sends a new UUID with a create, so a repeated request finds its first answer.
    id: uuid("id").primaryKey().defaultRandom(),
    userId: uuid("user_id")
      .notNull()
      .references(() => users.id, { onDelete: "cascade" }),
    name: text("name").notNull(),
    // Where the meal comes from, such as a delivery service. One free-text tag, trimmed.
    source: text("source"),
    // Total figures for one meal, as read from a label or a menu. All four required.
    energyKcal: numeric("energy_kcal", { precision: 6, scale: 1, mode: "number" }).notNull(),
    proteinG: numeric("protein_g", { precision: 5, scale: 1, mode: "number" }).notNull(),
    carbsG: numeric("carbs_g", { precision: 5, scale: 1, mode: "number" }).notNull(),
    fatG: numeric("fat_g", { precision: 5, scale: 1, mode: "number" }).notNull(),
    archivedAt: timestamp("archived_at", { withTimezone: true }),
    // Deleted by the user while entries use it. Invisible everywhere but on those entries.
    deletedAt: timestamp("deleted_at", { withTimezone: true }),
    createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [
    check(
      "saved_meals_values_in_range",
      sql`${t.energyKcal} BETWEEN 0 AND 10000 AND ${t.proteinG} BETWEEN 0 AND 1000 AND ${t.carbsG} BETWEEN 0 AND 1000 AND ${t.fatG} BETWEEN 0 AND 1000`,
    ),
    // (review) The target of the composite key from entries.
    uniqueIndex("saved_meals_id_user_uq").on(t.id, t.userId),
    index("saved_meals_user_id_idx").on(t.userId),
  ],
);
```

### Entries

```ts
// apps/backend/src/db/schema/entries.ts
// Text with CHECKs, not pgEnum: step 5 adds the kind "recipe", and an
// ALTER TYPE ... ADD VALUE cannot be used in the migrator's own transaction.
export const ENTRY_KINDS = ["food", "saved_meal", "estimate"] as const;
export const ENTRY_STATUSES = ["planned", "eaten"] as const;

export const entries = pgTable(
  "entries",
  {
    // The web sends a new UUID with every add and copy, so a repeated request applies once.
    id: uuid("id").primaryKey().defaultRandom(),
    userId: uuid("user_id")
      .notNull()
      .references(() => users.id, { onDelete: "cascade" }),
    date: date("date", { mode: "string" }).notNull(),
    // The order within a day: the order entries were added. From the sequence
    // on insert, never changed, so a move keeps it and an undo restores it.
    position: bigserial("position", { mode: "number" }).notNull(),
    status: text("status").$type<(typeof ENTRY_STATUSES)[number]>().notNull(),
```

### Rules the schema and services carry

- **How an entry keeps its figures** (review, FR-DAY-07, FR-DAY-09). An entry stores its **basis** and its **amount**, and its figures are computed from those two alone (section g, decision 5). `addEntry` writes the basis from the source, read `FOR SHARE`. Nothing else writes it, except the rewrite below. An amount edit, a move, a status change and an undo keep it. `copyEntries` copies the source entry's basis and references as they are. One rule, with no branch for a hidden source.
- **An amount edit on a food entry** takes grams as given, or a portion count times the portion's current grams when the portion is still visible (`portion_not_found` when not). The basis stays.
- **The portion hint** (review 2). `portion_id` is read only through the join above: same id, same food as the entry, visible to the user. An id of another food or another user's portion is ignored. A removed portion leaves the entry intact, and `lastAmount.portion.id` and the entry's `portion.id` answer null, so the web offers grams. The figures never pass through it.
- **Editing a source** (0.1). `updateOwnFood` and `updateSavedMeal` update the source row first, then, in the same transaction, set the basis of its entries `WHERE status = 'planned' AND date >= ctx.today`. Because `addEntry` reads the source `FOR SHARE`, an add in flight either commits before the edit's row lock is granted, and the rewrite (a later statement) sees it, or waits for the edit and reads the new values. Archiving changes nothing. A Fineli re-import changes no entry.
- **Deleting a source** (0.11). One transaction: lock the row (`FOR UPDATE`), check `EXISTS (SELECT 1 FROM entries WHERE food_id = $id)` in a new statement, then delete outright when unused, or set `deleted_at` (and clear the food's `barcode`, and delete its favourite rows) when used. The lock waits for an add holding `FOR KEY SHARE` through its foreign key, so the check sees that add, and the outright delete never cascades away an entry added a moment earlier. A hidden row is never purged later: it is invisible, it carries no figures any day reads, and it goes with the account.
- **Cascade.** `entries` and `saved_meals` carry `user_id` and reach `users` through cascading keys. `entries.food_id` cascades from `foods`, and the composite meal key from `saved_meals`. Neither fires on a user action: a Fineli food is never deleted, and a used own food or meal is hidden. `seedOneOfEach` seeds one saved meal and **one** entry (a saved-meal entry), because the deletion test expects one row per table per user.
- **Positions.** `bigserial`. An add and every copy take the next value, a copy in its source order. A move keeps it, and a restore brings back the old one (review 2). Equal positions sort by id.
- **Removed entries** (review 2). `removeEntry` moves the entry's full row into `removed_entries` in the same transaction and deletes it from `entries`. `POST /entries/:id/restore` moves it back exactly: the same id, position, basis, amount, references and status. It never re-reads a source, so it works on a hidden one. A row older than ten minutes is not restorable (`entry_not_found`), and each `removeEntry` deletes the user's rows older than ten minutes. An add or a "Save and log" whose entry id is in `removed_entries` adds nothing (section d), so a late retry cannot bring back an entry the user undid or removed.
- **Statuses.** `eaten_at` is set to `ctx.now` on becoming eaten and cleared on becoming planned. The future rule is 0.2.
- **Ownership.** An entry points only at a food the user can see (`visibleFood`) and a saved meal of their own that is not deleted. An archived meal and a retired Fineli food can be logged.

### Rounding and positions, stated once (review)

- **A row** is computed exactly in integers and rounded once: kcal to a whole number, grams to one decimal, halves away from zero.
- **A total** (each reading of a day, and each week row) is **the sum of its rows' rounded figures**, so the rows on screen always add up to the total, for the user and for an assistant summing them. A total can differ from the exact sum by up to half a unit per entry: twenty entries, at most 10 kcal.
- **A position** compares the total with the range in integer tenths: below when `total < lower`, within when `lower <= total <= upper`, above when `total > upper`. The distance is `lower - total`, `upper - total` or `total - upper`, also in integer tenths, answered to one decimal. Bounds have one decimal and kcal totals are whole, so a kcal distance can end in .5. The screen shows a distance as the range shows its bounds: whole when its tenths are zero ("120 kcal"), with its decimal otherwise ("959.5 kcal"). 130 minus 129.9 is 0.1 g, never 0.09999999999999432.

**"Today" stays true after midnight** (review, 0.16). Three parts:

1. `useDayClock` computes `todayIn(me.timeZone, now)` on the phone, on every `visibilitychange` to visible and once a minute. `me.timeZone` is the user's stored zone, the one the server's `ctx.today` uses. When it differs from the cached day answer's `today`, the Day tab treats its data as stale: the summary and list show their loading frame, the launcher and every mark button are disabled, and `["days"]` and `["targets"]` refetch. Nothing can log onto yesterday from a stale answer, however slow the refetch.
2. Day queries and `["targets"]` set `refetchOnWindowFocus: true` and `refetchOnReconnect: true`.
3. A time-zone change written by `deviceTimeZone.ts` invalidates `["days"]` with `["me"]` and `["targets"]`. Own-food and saved-meal edits invalidate `["days"]`, because the planned-entry rewrite (0.1) changes days those writes do not answer.

The label "Today" comes from the day answer's own `today`.

**Ids, minted once per action** (review, review 2). `pendingIds.ts` holds one id per unconfirmed write. An id is cleared by the first of: a success answer, **any day answer (from any query) that contains an entry with that id**, or 60 seconds after it was minted. So a write that landed while its answer was lost is recognised as soon as the day refreshes, and a pending id never outlives the moment:

- **A form** (the log view, `EntrySheet` for a copy, `SavedMealSheet`, `EstimateSheet`) mints its id when it opens, and keeps it across every Save until one succeeds. A canteen timeout followed by a second tap on Log resends the same id.
- **A "+"** mints its id on press under the key `(date, kind, sourceId)`. A second press within the id's life resends it, so a timeout followed by a second tap cannot duplicate. (review 2) After the id is cleared, the next press mints a new one, so a second shake that afternoon is a second entry.
- **A copy** mints one id per source entry when its sheet opens.
- **Status changes, moves and edits** set a state, so a repeat is harmless and needs no id.
- (review 2) **A replay is said plainly.** When an add answers `outcome: "replayed"` (the first send had landed), the toast says "Already logged {name}." with **"Log another"**, which logs with a fresh id. It never says "Logged" for a write it did not make. A replay with `entry: null` (the entry was undone or removed since) shows "This was removed. Log another?" with "Log another".

**Quick log, two taps.** Tap 1, the launcher, opens `FoodSheet` with the day's date and relation. Tap 2, "+" on a recent row, calls `addEntry` with its pending id, the day's date, status eaten on today and past days (planned on a future day), and the last amount (`{ portionId, count }` when the portion still exists, else `{ grams }`). The server reads the food `FOR SHARE`, writes the basis, inserts, reads the day and answers `{ entry, days }`. The web writes each day into the cache (and into `["days", "day", "today"]` when its date matches), invalidates `["days", "range"]` and `["log"]`, closes the sheet and shows "Logged Rahka, 200 g." with Undo.

**Undo.** An add is undone by `DELETE /entries/:id`. A mark by `POST /entries/status` with `planned` and the answered `changedIds`. (review 2) A remove by `POST /entries/:id/restore`, which brings back the stored row exactly, figures and references included, and works on a hidden source. A move by `PATCH` with the old date and, when the move turned the entry planned (0.2), `status: eaten`. Every undo is exact (review).

**Marking eaten.** The circle sends `PATCH /entries/:id { status: "eaten" }`, shows a busy ring and ignores taps until it settles. The answered day replaces the cached one, so the row and both readings change in one frame. "Mark all eaten" sends the ids of the planned entries on screen.

**Editing.** `EntrySheet` Save sends only the changed fields. A date change is a move. The toast says "Moved to Tue 17 Nov." with Undo.

**Copying** (PR 3d). `CopyEntriesSheet` sends `POST /entries/copy` with the ids it minted. Copies arrive planned with their source entries' basis (review). The toast says "Copied 3 entries to Wed 18 Nov." with Show.

**Weak signal and no connection** (0.7). Nothing is queued.

- Known offline (`useOnlineStatus` false, or the auth status `offline`): nothing is sent. The toast says "You are offline. Changes need a connection."
- A timeout or a network failure: the write may have landed. (review) A sheet keeps its values and shows "Could not confirm. Check your connection and try again." under its footer. A one-tap action shows the same line in the toast with Try again. A retry sends the same request with the same id. A request that did land answers its first result again, so nothing duplicates.
- A 4xx is a real refusal and shows its code's copy.

**Deleting a used own food.** `deleteOwnFood` hides it. Every day keeps its rows and figures. A future planned entry keeps its values, and its sheet says "This food is no longer in your foods."

**Errors.** A 404 `entry_not_found` on a write closes the sheet, refetches the day and shows "This entry is no longer there."

**The gauge, exactly** (`Gauge.tsx`, `size="day" | "mini"`) (review):

- **Scale, fixed per day.** From 0 to `S = upper × 1.25`, the range's own upper bound. - **Track.** A pill, 14px tall on a phone and 16px from `md`, the full content width, `--color-gauge-track`.
- **Range band.** From `x(lower)` to `x(upper)`, `--color-gauge-range`, a neutral warm grey in both themes.

## g) Constraints and decisions

1. **Four pull requests** (review): backend, the Day tab, the log sheet, then the week view and copying. Each leaves `master` green. The app logs from the end of 3c, and has the whole step at the end of 3d.
2. **No `days` table.** A day is the entries on a date. A row per day would hold nothing but its key.
3. **An entry stores basis and amount, not figures**, and the basis is written once (review). One computation from two stored values. Step 5's servings are a fourth scale of the same function.
4. **Typed amount columns per kind** (`grams`, `meal_count`, later `servings`), so a CHECK says what each kind uses.
5. **Figures are computed in integers, in one shared function.** Each basis scaled to thousandths, grams × 10, counts × 100, integer products, one rounding per row with halves away from zero, totals summed in integer tenths, positions compared and subtracted in integer tenths. Floating point gets real cases wrong: 4.02 g per 100 g × 250 g is exactly 10.05 g, and `4.02 * 250 / 100` is 10.049999999999999, which rounds to 10.0. The server and the live preview call the same function. Largest value: a basis of 10000 kcal in thousandths (10^7) times a count of 100 in hundredths (10^4), normalised by 10, is 10^12 per entry, below 2^53.
6. **A total is the sum of rounded rows** (review, 0.14), so a screen and an assistant always add up the same way.
7. **Positions are computed by the server.** The client picks copy by the position enum and formats the distance.
8. **Client-chosen ids make adds, copies and "Save and log" idempotent.** `INSERT … ON CONFLICT (id) DO NOTHING RETURNING`, then a read by id and user. Each id lives until its write succeeds (section e).
9. **Writes answer the changed days.** One round trip per action on a weak signal.
10. **The week reads one range query** with `inForceOn`, the pure form of `targetsOn`'s rule, pinned by a parity test.
11. **One undo surface**, the toast, mounted once.
12. **The log sheet stays step 2's sheet.** Create actions, recent items, saved meals and the log block join its views.
13. **Saved meals are searched in the browser** over the loaded list. It filters and computes nothing.
14. **A fixed gauge scale per day** (review). Ticks and band move only when targets change.

### R2. Today, midnight and resume (stated once)

**The one rule.** The date the app treats as today is the server's. The device's clock never decides a date. It only says when to ask the server again. `apps/web/README.md` ("Numbers and dates") already says "Today comes from the server's answer, never from this device's clock". That stays true, and 3b adds one sentence: "The device's clock only decides when to ask again."

**Pieces** (3b):

- `todayIn(timeZone, now)` in `lib/localDate.ts`: the `YYYY-MM-DD` that `now` falls on in `timeZone`, through `Intl.DateTimeFormat` with `timeZone`. A zone `canonicalTimeZone` (from `packages/types`) does not know falls back to `DEFAULT_TIME_ZONE`, as the server does.
- `TodayProvider` in `components/targets/TodayProvider.tsx`, **rendered once, by `TargetsGate`, around the shell**, the component that already owns the device time zone sync. It holds the state below in one React context, so the gate is the single mount and every other component reads it through `useToday()`. One mount covers the Day tab and Settings ("In force today", the targets sheet's default date) alike, which closes the `TODO.md` item "Refresh today across midnight".
- `useToday()` in `hooks/useToday.ts` reads the context: `{ today: string | null, holding: boolean, confirm: "fresh" | "checking" | "paused" | "failed" }`.
- `noteServerToday(today)`, exported from the same module and called with the `today` of every answer that carries one: the targets read, every day read (in `dayQuery`'s fetch) and every write answer (in `afterEntryWrite`, for each answered day).

**The state the provider keeps:**

- `serverToday`: the newest `today` any server answer has carried, compared as `YYYY-MM-DD` strings. It starts as `["targets"].data.today` and only ever moves forward. It is null while no answer has arrived (R3 has the screen for that).
- `lastAskSettledAt` and the last ask's outcome: when the provider last asked the server because of the device's clock, and how it ended.

**Triggers and what each refreshes:**

| Event                                                                                                                                                                                       | What happens                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| The page becomes visible (`visibilitychange`, the event TanStack's focus manager listens to)                                                                                                | Every query under `["days"]`, `["targets"]` and (3c) `["log", "recents"]` older than `STALE.live` (30 s) with an observer reads again: `refetchOnWindowFocus: true` on `dayQuery`, `targetsQuery`, `targetsOnQuery` and `recentsQuery`. The global default in `queryClient.ts` stays off. Then the device check below                                                                                                          |
| The connection returns                                                                                                                                                                      | The same queries (`refetchOnReconnect: true`). Then the device check, without its 5-minute bound when the last check failed or was paused                                                                                                                                                                                                                                                                                      |
| **A server answer moves today.** `noteServerToday` receives a `today` newer than `serverToday`, from any source: a refetched targets answer, a day read, a write answer                     | `serverToday` moves to it, and the provider runs `afterDayChange(client)` once for that new date: `refresh(client, [queryKeys.targets(), queryKeys.days()])` in `invalidation.ts`. Every cached day's `relation`, `unmarkedCount` and default state are now from the old date, so every day key is read again. This is the path that usually fires, because a write or a read after the server's midnight carries the new date |
| **The device check.** On `pageshow`, on becoming visible, on reconnect and on a 60 s tick while visible: `deviceToday = todayIn(me.timeZone, Date.now())`. When `deviceToday > serverToday` | It asks: `refresh(client, [queryKeys.targets()])`, **at most once every 5 minutes** while the device date stays ahead (the 60 s tick only compares, it sends nothing sooner). When the answer carries a newer today, the row above runs. When it carries the same today, the server's date stands for now and the next ask waits 5 minutes                                                                                     |

When `deviceToday < serverToday` (a slow clock), nothing is asked: the server has already moved, and every answer keeps the screen on its date.

`me.timeZone` is read from `["me"]` (`meQuery`), which `afterTimeZoneChange` updates, falling back to the auth context's user.

**A fast clock, worked.** The device runs 5 minutes ahead of the server. At device 23:55 the device date is still the old one, nothing is asked. At device 00:00 (server 23:55) the check asks: the answer carries the old date, which stands. The 60 s ticks at device 00:01 to 00:04 send nothing. At device 00:05 (server 00:00) it asks again: the answer carries the new date, today moves, and `afterDayChange` runs once. Usually a read or a write after the server's midnight has moved today before that. A clock any amount ahead costs one read per 5 minutes until the server's midnight, and the date moves at most 5 minutes late. A clock hours ahead asks every 5 minutes for those hours, while the page is visible, which is cheap. A device that is minutes slow reaches its own midnight late, but any read or write after the server's midnight moves today first.

**The outcome of an ask:**

| Outcome                  | `holding` | Today                       | `confirm`  | Next ask                                              |
| ------------------------ | --------- | --------------------------- | ---------- | ----------------------------------------------------- |
| In flight                | true      | no                          | `checking` |                                                       |
| Success, today moved     | false     | the new server today        | `fresh`    | none: the dates agree                                 |
| Success, same today      | false     | the server's today stands   | `fresh`    | after 5 minutes, while the device date is still ahead |
| Error (a 5xx, a timeout) | false     | the last server today stays | `failed`   | on reconnect, or the next trigger after 5 minutes     |
| Paused (offline)         | false     | the last server today stays | `paused`   | on reconnect, at once                                 |

`holding` therefore lasts only while the ask is in flight, normally under a second. It never outlives a failure or an offline pause. Only a successful answer moves or confirms today. A failed or paused ask leaves the last server today in place and is asked again.

**While `holding`:** every write control on the Day tab and in an open log sheet or entry sheet is held: `aria-disabled`, a press sends nothing. The marks, "Mark all eaten", the launcher, "+", Log, Save and Remove all read it. **Undo is not held** (R3, toasts). No new copy: the hold ends before a person can read a line.

**While the device date is ahead and the last ask did not succeed** (`deviceToday > serverToday` and `confirm` is `checking`, `paused` or `failed`), the Day tab showing today without `?date=` does not show the cached day, which belongs to the server's older date. It shows the state of the ask in its frame (R3): the loading frame while `checking`, "This day needs a connection." while `paused`, "This day did not load." with Try again while `failed`. A Day tab with `?date=` keeps its content, because its date is still right.

**An open sheet with typed values survives all of it.** Nothing above a sheet unmounts on these refreshes:

- `TargetsGate` keeps the shell once it has decided (it already does), whatever `["targets"]` is doing. `TodayProvider` renders its children unconditionally.
- `DayTab` is never keyed by date. Its sheets are mounted at the `DayTab` level through `useSheetTarget`, above the date-keyed content.
- A form's values live in the form. No refetch writes into a field. A `FormSheet` with input refuses dismissal.
- A sheet's date is the one it opened with. The log sheet keeps logging to that date after midnight, and its header line, which reads `useToday()` live, turns from "Logging to today" into "Logging to yesterday" in its reserved line, so the person sees it (R5). The entry sheet's "Eaten" choice, disabled for a future date, re-reads `useToday()` too, so tomorrow's entry can be marked eaten after midnight.

#### Entry sheet body per kind

Every field is prefilled **from the entry itself** when the sheet opens, and nothing that loads later rewrites a field or moves the chip the person sees.

- **Food:** `AmountField`.

The entry's own portion chip is built from the entry at open when `entry.portion` is set and its `id` is not null: its label from `portion.unit` (the catalog's unit name) or `portion.name`, its grams per portion `entry.grams / portion.count`.   - **Preview.** While the amount is as saved, `MacroFigures` shows `entry.figures`, the server's own. **The inverse for Undo** (`entryForm.ts`) is computed from **the entry as it was before the save and the entry the save answered**, never from the PATCH sent, because the server can change a field it was not sent: a move of an eaten entry to a future date turns it planned. Two limits, stated in the code and in `quick-logging.md`'s undo section, which already says the second:

- An old amount entered as a portion is sent back as `{ portionId, count }`, and the server weighs it at the portion's grams today. When the portion was edited between the save and the Undo, the grams differ. When the portion is gone, the inverse sends `{ grams }` instead.
- A status round trip resets `eatenAt`: an entry eaten, planned and eaten again counts as eaten at the last mark (its place in recent items moves).

#### What each write puts in the cache (3b)

All in `lib/invalidation.ts`, following 2d's fix-cycle pattern: the write's own answer first, then a refresh of what it made stale.

- `afterEntryWrite(client, days, shownDate)`: cancels reads in flight for each answered day's key, `setQueryData(queryKeys.day(d.date), d)` for each, and passes each day's `today` to `noteServerToday`. **When the answer holds no day for `shownDate`, it refreshes `queryKeys.day(shownDate)`**: the status route answers only the dates it changed, so a mark that changed nothing (another device marked it, a Try again after a mark that had landed) answers `days: []`, and only a read shows the row as it is. Then `refresh(client, [["days", "range"], queryKeys.log(), queryKeys.savedMeals(), queryKeys.foodFavourites(), queryKeys.foodDetails()])`. The answered days are fresh and are not read again. Recents, last amounts and last counts change with eaten entries, so their keys refresh. #### Undo, failures and the toast (3b)

- A toast is one at a time: `show()` closes the one showing, then adds the next, so no older toast stays in the DOM. 6 s, paused while pointed at or focused, swipe down to dismiss, `role="status"` (Base UI's polite priority).
- **Placement:** above the tab bar on a phone (`bottom: calc(var(--spacing-tab-bar) + var(--safe-bottom) + 0.5rem)`, from the token the tab bar itself uses), at the bottom of the content column from `md`. `zToast` (40) is under the sheets (50), so an open sheet always covers a toast and a toast never covers a sheet's footer. A toast is never the place a sheet's own outcome shows: Base UI's drawer treats a press outside it as a dismissal, so a toast button over a sheet would close the sheet.
- **A one-tap action on the page** (mark, mark all): known offline, nothing sent and the offline toast. A timeout or network failure: "Could not confirm. Check your connection and try again." with "Try again", which resends the same request (status changes set a state, so a repeat is harmless). A 4xx: the code's copy. `entry_not_found`: the day refetches and the toast says "This entry is no longer there."
- **A sheet's action** (Save, Remove entry): the sheet stays open and shows the failure in its refusal line, with the typed values kept. On success the sheet closes and the toast shows.
- **Undo.** A press closes the toast at once, so it cannot be sent twice. Undo is **not** held by `holding`: it names explicit ids and dates, so a midnight changes nothing it sends. Every inverse is idempotent (a status set, a restore that answers 200 when the entry is back, a PATCH to values, a DELETE), so a failed Undo shows "Could not undo." with "Try again", which sends the same inverse. A 404 `entry_not_found` on the DELETE that undoes an add counts as undone: the entry is gone either way.

## Deviations in PR 3a (backend engineer, 2026-11-16)

What the build does differently from sections b to d, and why. Each was checked against the exit list of step 3a.1.

1. **Migration `0004_days_and_logging.sql`, not 0003.** Master took 0003 for refresh token families.
2. **`saved_meals_id_user_uq` is a `unique()` constraint, not a `uniqueIndex`.** Drizzle emits every foreign key before every index, so the composite key from `entries` would be added before the unique index it needs and the migration would fail. A table constraint is created inside `CREATE TABLE`. Same guarantee, no hand-written SQL.
3. **`removed_entries.row` is the entry as `to_jsonb(entries.*)` writes it**, keyed by column name, typed `Record<string, unknown>`. A restore runs `INSERT INTO entries SELECT (jsonb_populate_record(NULL::entries, row)).*`, so every column, a future one included, comes back exactly with no hand-kept mapping. The design typed it as `$inferSelect`, which does not match what Postgres writes.
4. **Where shapes live.** `RangePositionSchema` is in `figures.ts`, because `positionOf` returns it. `EntryWriteResultSchema` and the other write answers are in `results.ts` (fix cycle 1, they were in `days.ts`), which imports `days.ts`, `entries.ts` and `savedMeals.ts`. In `entries.ts` they would make it and `days.ts` import each other. `LastAmountSchema` is in `foods.ts`, because `FoodDetailSchema` needs it. `ENTRY_KINDS` and `ENTRY_STATUSES` are in `packages/types/src/entries.ts`, and the schema builds its CHECKs from them.
5. **`FoodAmountSchema` is one strict object with a refinement, not a union.** A Zod union refuses with a generic message, so a bad weight would answer `invalid_request` instead of `entry_grams_invalid`.
6. **The user lock is `FOR KEY SHARE`, taken first by every entry and saved meal write and by the own food edit and delete** (`lockUserForWrite` in `sourceValues.ts`). The design locks only source rows. Without a user lock first, an add holds the food `FOR SHARE` and then its foreign key asks for the user row, while an account deletion holds the user row and its cascade asks for the food: a deadlock pair. `FOR KEY SHARE` is the lock the foreign key takes anyway. It conflicts only with the deletion's `FOR UPDATE`, so it adds no pair with session and target writes (`FOR NO KEY UPDATE`), and logging never queues behind a session renewal. The brief asked for `FOR NO KEY UPDATE` wherever the design locks. The design never locks the user row, and `FOR NO KEY UPDATE` would serialise every add behind renewals and target writes, which `targets.db.test.ts` documents adds do not do.
7. **A portion count whose weight rounds to 0 g or exceeds 5000 g answers 400 `entry_grams_invalid`.** `grams` is `numeric(5,1)` and must be above zero. The design did not say.
8. **`WriteOutcome` gains `replayed`.** An add, a copy and a save-and-log that wrote nothing say so to the route and the coming tools.
9. **`setEntriesStatus` skips entries already in the status**, so `changedIds` is exactly what an undo must change back. Its `days` are the dates of the changed entries, empty when none changed.
10. **A restore of an entry that is in `entries` answers 200 `replayed`**, whether it was restored a moment ago or never removed.
11. **A copy skips a new id the user already holds or removed**, as an add does, and answers `replayed` when it skipped them all. Repeated new ids in one copy answer `invalid_request`.
12. **`PUT /saved-meals/:id` takes `SavedMealEditBodySchema`**, the body without `id`. **`POST /saved-meals/log` answers the meal read after the log**, so its `lastCount` includes the entry.
13. **Saved meal names have no searchability check.** The web filters the loaded list in the browser by any substring of the name or the source, so a name like "M&M" is still found. The list sorts with `byName` (`fi-x-icu`) as own foods do.
14. **A hidden own food is also left out of `listOwnFoods` and of the `ownFood` WHERE** every own food write uses, so it answers 404 to every write. The delete and hide name the owner in their own WHERE, as every food write does.
15. **`foodWrites.db.test.ts`'s `interfered` wrapper follows a transaction, and gains the kind `transaction`.** The own food edit and delete now run in a transaction, so a hook on `db.update` or `db.delete` never fired. The delete's owner-change test hooks the transaction's start, which is now the point between the check and the write.
16. **Link map.** The homes "the log sheet" and "without a connection" are left for 3c and 3b, because they describe screens that do not exist yet. A home "Ids, replays and restores" in `days.md` was added. `apps/web/README.md` is unchanged: 3a touches only `errorCopy.ts` in the web.
17. **New constants**: `MAX_FIGURE_G`, `MAX_ENTRY_BATCH`, `MAX_DAY_RANGE`, `MAX_MEAL_SOURCE_LENGTH`, `DEFAULT_RECENTS_LIMIT` and `MAX_RECENTS_LIMIT`.

### Fix cycle 1 (backend engineer, 2026-11-16)

18. **A write that races an account deletion answers 404 `user_not_found`.** `lockUserForWrite` throws it when the user row is gone, the code `contextFor` answers for a deleted user's live token. `createSavedMeal` now runs in a transaction that takes the lock first, and `saveAndLog` takes it before it calls `createSavedMeal`. The users foreign keys `entries_user_id_users_id_fk` and `saved_meals_user_id_users_id_fk` map to the same answer as a second line of defence. `setSavedMealArchived` takes no user lock: it is one UPDATE of the meal row, holds no other lock and cannot deadlock, and a meal the deletion took answers 404 `saved_meal_not_found`. `deletionRaces.db.test.ts` pins all five.
19. **A copy answers `replayed` whenever it inserted nothing**, not only on a full replay it saw up front. A repeat of the same copy that meets the first one's uncommitted rows waits on them, inserts nothing, and answers 200 `replayed`. After its inserts it re-reads the ids it could not insert and answers 409 `entry_id_taken` only when another user holds one.
20. **The status batch and the planned rewrite lock their entries in id order** (`SELECT id ... ORDER BY id FOR NO KEY UPDATE`, then the UPDATE on those ids). The rewrite is `rewritePlannedBasis` in `sourceValues.ts`, shared by food and meal edits. A deadlock (40P01) anywhere answers the busy 503 with `Retry-After`.
21. **A restore clears the user's expired rows, as a remove does, and a stored row the table refuses answers `entry_not_found`.** 23502, 23514 and 22P02 from the restore's insert mean a row removed before a migration changed `entries`. The schema of `entries` and the backend README say such a migration rewrites or clears `removed_entries.row`.
22. **`entries_user_eaten_idx` is `(user_id, eaten_at DESC, position DESC) WHERE eaten_at IS NOT NULL`**, and `listRecents` walks it with a recursive query: each step takes the next older eaten entry whose source is new and usable, and the walk stops at the limit. On a user with 43 000 eaten entries over 325 sources, the `DISTINCT ON` query read every eaten row and sorted 3 MB on disk in 90 ms. The walk reads 83 buffers in 0.5 ms. Same result: eaten only, distinct, newest first, ties by position, archived and deleted sources left out, a gone portion's id null. Migration 0004 is regenerated with the new index.
23. **The use check names the user** (`isUsed` in `sourceValues.ts`), on `entries` and on `removed_entries`, so `removed_entries` is read by `removed_entries_user_removed_idx`. On 60 000 rows of other users it went from a 26 ms sequential scan to 0.1 ms.

### Where 3c ended up, against the design (documentation specialist, 2026-11-17)

Later items above replace earlier ones. Read this list first; the numbered items hold the measurements and the reasons.

- **The close wait → the closing layer.** Part 1's `ARM_DELAY_MS` wait before a log closes the sheet (part 1, deviation 4) is gone. A closing sheet's backdrop swallows every press until Base UI ends its exit (`closingBackdropStyle`, `closingBackdropHandlers` in `components/ui/closingSheet.ts`), and afterwards `useClosingPresses` drops only a press within 24 px of the closing press until 500 ms after it (fix cycle 2 item 4, replacing fix cycle 1 item 3's "every press for 500 ms"). The log sheet closes as the answer lands.
- **The row of four → two by two.** `FigureFields` is two by two at every width (fix cycle 2 item 5, replacing fix cycle 1 item 4's row of four from `md`). The shared line keeps two lines on a phone and one from `md` (`lineRoom(2, 1)`). `DecimalField.unitRoom` has three sizes. The log block's read-only figures (`MacroFigures layout="row"`) stay one row.
- **Where the adds live: `useAddActions`.** `add`, `saveAndLog` and `withdrawAdd`, their toasts, undo and "Log another", composed by `useEntryActions` (part 2 deviation 5). `sendAdd` holds the pending id and reads the day again after an unconfirmed failure (fix cycle 2 item 2).
- **The retry rule.** The latest press decides (`components/log/mealSends.ts`, fix cycle 1 item 1). A new entry id only when the `DELETE` removed one, a 404 keeps it (fix cycle 2 item 1). A "+" that could not confirm holds its id for `UNCONFIRMED_HOLD_MS`, six seconds, equal to `STATUS_MESSAGE_MS` (fix cycle 2 item 3). The residual (j3: the first request landing between the `PUT`'s 404 and the second send) is in `TODO.md` with its server-side fix.
- **The status line's one store.** `useStatusMessage` in `StatusLine.tsx` holds one message with a tone: failures of "+", archive and restore in the accent, "Saved {name}." after Save meal or an edit in ink (part 2 deviation 1). The latest replaces the last, and it clears after six seconds or at the next press or key.
- **The saved meal sheet's order.** Eaten or planned first, then Name, From with its chips, and Per meal (the ui-validator's reorder, part 2 "Fit"). From `md` the choice sits beside Name and From takes the full width (`pairRow`); an edit puts Name and From in one row. The estimate sheet asks the choice first too, beside the name from `md` (`EstimateFields.besideName`). "Save meal" keeps its footer row while typing; only the entry sheet's Remove entry yields (`yieldsToKeyboard`).
- **One offline line.** `FormSheet` takes `FormFailure` (`{ line, cause }`) and shows `common.offline` for a failure the connection explains while the app knew it was offline (fix cycle 1 item 5).
