**The problem, stripped of the proposed mechanism.** A user must have their own two ranges before any figure appears, and must be able to move them over time without rewriting history. Every food a user can log must carry trustworthy figures per 100 g from one place, findable in seconds by an everyday word. The brief proposes no UI mechanism beyond "the first-run gate", which the scaffold design already placed in `(app)/layout.tsx`. That placement needs no workaround.

**Changes proposed that were not asked for** (each is also in section h):

1. Removing a dated targets change (0.4).
2. Retiring Fineli foods that leave a release, rather than deleting them (0.6).
3. The import's guard that refuses to retire more than 10 % of live Fineli foods without `--allow-retire`.

**Requirements drift** (Artur decides, nobody edits the files):

- **FR-TGT-04** (review). The design ships the literal reading: every targets form starts empty, and a later change shows the targets in force as text. Proposed wording, so that prefill can come later as a one-line change: "FR-TGT-04: The system shall offer no default, example or computed value for a target. A user's first targets start empty. A later change may start from the user's own targets in force on its date."
- **FR-TGT-03 against FR-AUTH-07** (review). Read strictly, FR-TGT-03 keeps a user without targets from deleting their account unless they invent targets first. The design puts Sign out and Delete account on the first-run screen. Proposed wording: "FR-TGT-03: The system shall ask a new user for both ranges before it shows any other part of the app. Signing out and deleting the account stay available."
- **Overview, Reference data, Fineli.** "It covers generic foods" undersells it. Release 18 holds 1,437 foods and 2,621 dishes, and some branded products. Proposed: "It covers generic foods and common dishes, with names in Finnish, Swedish and English."

## a) Overview

Step 2 gives every account its own targets and a food catalogue. Targets are a calorie range and a protein range that change from a date the user picks, and a new account cannot reach the app until it has them. The catalogue holds the Fineli foods, loaded by a repeatable import, and each user's own foods, with portions and favourites. One search finds a food by any part of its Finnish or English name and ranks the everyday match first. Step 3 builds the day and quick logging on top of the read services, the search sheet and the per-100 g figures this step ships.

CREATE EXTENSION IF NOT EXISTS pg_trgm SCHEMA public;   -- (review) f_unaccent names public
CREATE EXTENSION IF NOT EXISTS unaccent SCHEMA public;
-- unaccent() is STABLE, so a generated column cannot call it. The usual immutable wrapper,
-- with the dictionary named so the search path cannot change its meaning.
CREATE FUNCTION f_unaccent(text) RETURNS text LANGUAGE sql IMMUTABLE PARALLEL SAFE STRICT
  AS $$ SELECT public.unaccent('public.unaccent'::regdictionary, $1) $$;
-- Lower case, accents folded (ä -> a, ö -> o), every run of non-alphanumerics one space, trimmed.
CREATE FUNCTION food_search_norm(text) RETURNS text LANGUAGE sql IMMUTABLE PARALLEL SAFE STRICT
  AS $$ SELECT btrim(regexp_replace(lower(f_unaccent($1)), '[^[:alnum:]]+', ' ', 'g')) $$;
-- (review) The head of a name: the first word of its first part, with hyphens kept, so
-- "Kananmuna, kuoreton" -> "kananmuna" and "Muna-kinkkuvuoka" -> "muna-kinkkuvuoka".
-- Parts are split on ", " (comma and space), never on a decimal comma such as "<0,5 %".
CREATE FUNCTION food_search_head(text) RETURNS text LANGUAGE sql IMMUTABLE PARALLEL SAFE STRICT
  AS $$ SELECT split_part(btrim(regexp_replace(lower(f_unaccent(split_part($1, ', ', 1))), '[^[:alnum:]-]+', ' ', 'g')), ' ', 1) $$;

- **One row is one dated change, holding the complete set in force from that date.** The set in force on a date is the row with the latest `effective_from` on or before it. Before the first row, it is the first row (0.2). Two changes on one date are one row. The API overwrites on a repeated date, and the web never does so silently: picking a date that already has a change switches the sheet to editing that change (section f) (review).
- **A change rewrites the days it covers** (review). Saving or removing a change on a past date changes the targets of every day from that date to the day before the next change. The first change also covers every day before it, so editing it changes those days too. FR-TGT-07 is about a new change leaving earlier days alone, and it holds. The feature doc says both plainly, and the sheet states the affected days before Save (section f).
- **Adding carbohydrate and fat later is two nullable column pairs and their CHECKs**, `carbs_g_lower` to `fat_g_upper`, with `NULL` meaning "not tracked". **Choosing what to track** makes `protein_g_*` nullable too, with a CHECK that both bounds of a pair are null together, and a CHECK that at least one pair is set. That is one `ALTER TABLE` and a schema change in the API, which is already keyed by nutrient (section d). Artur's settled wording allows "a new row or column".
- **Two caveats on "additive"** (review). Adding carbohydrate and fat is additive: optional keys in `TargetRanges`. Making protein optional is not: `proteinG` becomes optional in the response, so the web, the MCP tools and every step-3 consumer of `targetsOn` change in the same PR. **Different targets by weekday** (on the requirements' Later list) is a different shape: a change would hold up to seven sets, most likely a child table keyed by change and ISO weekday, with `targetsOn` choosing the change and then the weekday's set. That is a rewrite of the read and of the change shape, not a new column, and it is not designed for here.
- `numeric(…, 1)`: one decimal place, so 142.5 g is storable. Drizzle 0.45's `numeric` takes `mode: "number"`. The engineer confirms it against the installed version and falls back to `mode: "string"` with conversion in the service.
- The `(user_id, effective_from)` unique index also serves `targetsOn`, which reads with `ORDER BY effective_from DESC LIMIT 1`.

Rules the schema and the services carry:

- **One catalogue, three sources.** `source` is what FR-FOOD-07 shows. `open_food_facts` is in the enum now so the API type is complete. No row has it until step 6, which decides whether a scanned product is shared or per user. The two CHECKs make an owner and a Fineli id impossible on the wrong kind of row.
- **Names.** `name` is always present. The display name is `name` for `fi`, and `coalesce(name_en, name)` for `en`. A user's own food has one name, shown in both settings. Step 6 fills `name_en` for a product where Open Food Facts has one.
- **Values** are stored as the source gives them, to two or three decimals. The web rounds for display: kcal to whole numbers, grams to one decimal.
- **A Fineli food is never deleted**, only retired, so nothing that points at it is ever cascaded away (0.6).
- **A user's own food is deleted outright in step 2**, because only its own portions and favourites point at it, and both cascade. Step 3 changes that rule (see "Not painting step 3 into a corner").
- **Portions.** A Fineli portion has a unit code, no owner and no name. A user's portion has a name and an owner. Every user sees a food's unowned portions plus their own. `food_portions_fineli_unit_uq` lets the import upsert portions without changing their ids.
- **Cascade.** `target_changes`, `food_favourites`, `foods` and `food_portions` all reach `users` through cascading keys and all carry `user_id`, so the existing walk and deletion test cover them once `seedOneOfEach` seeds one of each. `SEEDED_TABLES` becomes `["food_favourites", "food_portions", "foods", "password_reset_tokens", "refresh_tokens", "target_changes"]`. The deletion test counts rows by `user_id`, so shared Fineli rows (null owner) are untouched by it. A new case asserts that deleting a user leaves every Fineli food and every Fineli portion, and removes the user's own portion on a Fineli food.
- **A user can point only at what they can see.** Favourites and portions are written only after `visibleTo` finds the food. The database alone would accept user B favouriting user A's own food, so the service is the guard, and each route has a test that B gets 404.
- **A user's own portion on a shared food is that user's alone** (review). User A's portion on a Fineli food hangs under a row every user sees. Every portion read and write therefore also passes `portionVisibleTo(userId)`: `getFood` loads `portions WHERE food_id = $id AND (user_id IS NULL OR user_id = $userId)`, and the portion routes find a portion by `id`, `food_id` and `portionVisibleTo` together, answering 404 `portion_not_found` otherwise, before the read-only check answers 403 for an unowned portion.

### The user's today (review)

- `users.time_zone` holds an IANA name. Every account starts with `Europe/Helsinki`, and the web app replaces it with the device's zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`) at the first app start after sign-in and whenever the device's zone differs from the stored one. `SettingsBodySchema` refuses a name `Intl` does not know (`invalid_time_zone`, no copy: no screen types it).
- `contextFor(req)` reads the user's zone and sets `ctx.today = calendarDate(ctx.now, timeZone)`, the `YYYY-MM-DD` that `Intl.DateTimeFormat("en-CA", { timeZone })` gives for `now`. A stored zone that the runtime no longer knows falls back to `Europe/Helsinki` with a log line. That fallback is the stated default for every account until its first device write.
- **A day boundary is the user's local midnight.** Days and targets are keyed by calendar date, never by timestamp, so a daylight-saving change never splits or doubles a day. Only "which date is today" depends on the clock. Tests pin `now` around both 2026 Helsinki switches: `2026-03-28T21:59:59Z` is the 28th and `2026-03-28T22:00:00Z` the 29th (UTC+2 before the spring switch at 01:00Z), `2026-03-29T20:59:59Z` is the 29th and `2026-03-29T21:00:00Z` the 30th (UTC+3 after it), `2026-10-24T20:59:59Z` is the 24th and `2026-10-24T21:00:00Z` the 25th (UTC+3 before the autumn switch at 01:00Z on the 25th), and `2026-10-25T21:59:59Z` is the 25th and `2026-10-25T22:00:00Z` the 26th (UTC+2 after it). Each pair was checked against Python's `zoneinfo`. A zone west of UTC (`America/New_York`) gives an earlier date than UTC for the same instant.
- Step 3 reads days for `ctx.today`, and step 4's tools take an optional date that defaults to it, so an assistant needs no device.

### The Fineli import (PR 2b)

**Command.** `pnpm --filter @hovimestari/backend fineli:import [dir] [--dry-run] [--allow-retire]`, a `tsx` script at `src/scripts/fineliImport/index.ts`, also built into `dist/` so the production image can run it. `dir` defaults to `apps/backend/data/fineli/`, which is git-ignored. It holds the unzipped release.

**Reading** (`readRelease.ts`, pure, no database):

1. Required files: `food.csv`, `foodname_FI.csv`, `foodname_EN.csv`, `component_value.csv`, `foodaddunit.csv`. A missing file or column fails with the file and column named. Columns are found by header name, never by position.
2. Decoding, **per file** (review), because release 18 mixes Windows-1252 name files with ASCII value files: UTF-8 if the bytes decode strictly, otherwise Windows-1252 (a superset of Latin-1). A BOM is dropped. Line ends CRLF or LF. Separator `;`. Parsed with `csv-parse` (mature, maintained, streaming), which also copes with quoting if a later release adds it.
3. Numbers: decimal comma or point. An empty value is missing.
4. The release label: the `Release.` line of `descript.txt` when present, printed in the report only.
5. Output per food: `fineliId`, `name` (FI), `nameEn`, `fineliType`, `fineliProcess`, `energyKcal = round(ENERC / 4.184, 2)`, `proteinG = PROT`, `carbsG = CHOAVL`, `fatG = FAT`, and portions for the units `KPL_S`, `KPL_M`, `KPL_L`, `KPL_VALM`, `PORTS`, `PORTM`, `PORTL`, `DL`, `RKL`, `TL`. Any other unit code is skipped and counted. Release 18 has no other in `foodaddunit.csv`, although its code list also names `PORTTBL`, `PORT1000KJ`, `KG` and `L` (review).
6. Left out, and counted: a food missing any of the four values (0.7), and a value outside the CHECK ranges.

**Applying** (`applyRelease.ts`), in one transaction, in batches of 500:

1. Upsert every food on `fineli_id`. A new id inserts a new row with a new UUID. A known id updates names, values, type and process, clears `retired_at`, and stamps `updated_at` only when something changed. **The UUID of a known Fineli food never changes**, so whatever points at it keeps pointing at the same food.
2. A food whose name starts with `(arc)` is upserted with `retired_at` set (unverified meaning, section 1).
3. Every live Fineli food absent from the release gets `retired_at = now()`. **Guard:** if that would retire more than 10 % of the live Fineli foods, the import stops before writing unless `--allow-retire` is given. A wrong directory or a truncated file cannot hide the catalogue.
4. Portions: upsert the release's unowned portions on `(food_id, fineli_unit)` and delete unowned portions whose unit is gone. A user's own portions are never touched.
5. `--dry-run` runs everything and rolls back.

**Report** (stdout): release label, foods inserted, updated, unchanged, retired, revived, left out (with reasons), portions inserted, updated, removed, and **every food whose Finnish name changed under the same id**, old and new side by side, so a person can see whether THL reused an id for a different food. Running the same release twice reports zero changes the second time.

**What happens to a food that disappears while entries point at it.** It is retired: search no longer finds it, its detail says so, favourites keep it, and every entry and recipe that points at it (steps 3 and 5) keeps its figures, because the row and its values stay.

**Where the file comes from.** Artur downloads the zip from Fineli's open data page in a browser and unzips it into `apps/backend/data/fineli/`. `docs/setup/fineli-import.md` holds the steps for local and for production. On Fly, the folder is copied to the machine with `flyctl ssh sftp` and the built script runs there with `node dist/scripts/fineliImport/index.js /tmp/fineli`, so no database password leaves Fly. CI and the tests never see the real release.

**Fixture.** `src/scripts/fineliImport/__tests__/fixtures/release-a/` and `release-b/`: about 25 foods in the exact release format (Windows-1252 name files, ASCII value files, CRLF, `;`, decimal commas), values invented. These test the import only. The ranking has its own sample of real names (section g, decision 6) (review). `release-b` changes one value, renames one food, drops one, adds one, drops one portion unit, and brings back a food `release-a` lacked. A `release-utf8/` copy covers the other encoding. A `README.md` in `fixtures/` credits THL Fineli under CC BY 4.0. `.gitattributes` marks the fixtures `binary`. ### Not painting step 3 into a corner

- Days read targets through `targetsOn(ctx, date)`, the function this step ships.
- An entry will point at `foods.id`, a UUID that a re-import never changes, and store its grams. A portion is a way to enter grams: an entry stores the grams and, for display, the portion's label and count, never a key to `food_portions`.
- FR-DAY-07 needs a past day's totals to survive an own food's edit and deletion. Step 3 should store the per-100 g figures on the entry when it is written, and turn deleting a referenced own food into setting a `deleted_at` (hidden from search and lists). An `entries.food_id` that cascades is then harmless, because the row is never deleted while referenced, and the cascade walk needs no exception. Step 3 decides. Nothing here blocks either way.
- Recent foods and the last amount (FR-LOG-03, 04) come from entries in step 3. No table is needed now.

/** Refused codes: target_required, target_value_invalid, target_not_positive, target_lower_above_upper. */
const bound = (max: number) => z.number(/* missing: target_required, NaN or >1 decimal or > max: target_value_invalid */)
  /* <= 0: target_not_positive */;
const range = (max: number) =>
  z.object({ lower: bound(max), upper: bound(max) })

## e) Data flow

**First run.** Sign-up lands on `/`. `AuthGuard` passes, `QueryProvider` mounts, `TargetsGate` reads `["targets"]`, `GET /targets` with no date (review). The answer has `changes: []`, so the gate renders `FirstRunTargets` instead of `AppShell`. The user types four numbers. The form parses each with `parseDecimalInput`, then the whole with `SetTargetsBodySchema`. Save sends `PUT /targets/<today>`, with `today` from the overview the gate already holds. `setTargets` upserts the row and answers it. The web invalidates `["targets"]`, the refetch has one change, and the gate renders the shell on the same URL.

**A dated change** (review). Settings, Targets, "Change targets" opens `TargetsSheet` with "Starts on" set to `today` and **four empty fields**. Above them a line states the targets in force on the chosen date, read from `["targets", { date }]` (`GET /targets?date=`), so the client never applies the in-force rule itself. Changing the date refetches that line. If the chosen date already has a change, the sheet switches to editing it: the title becomes "Targets from {date}" and Save overwrites that change, never silently. When the date is today or earlier, a line says which days the save changes (section f). Save sends `PUT /targets/<date>`. Days before `<date>` keep their targets, because `targetsOn` for them still finds the older row.

**Search.** The Day tab's launcher opens `FoodSheet` in its browse view, which reads `["foods", "favourites"]` and `["foods", "own"]`. Typing updates the field at once. `useDebouncedValue` passes the trimmed text after 150 ms, and from two characters `["foods", "search", q]` fetches with an `AbortSignal`, so a superseded request is cancelled. The previous results stay on screen until the new ones arrive (`placeholderData: keepPreviousData`), so the list never flashes empty. The server normalises the query in SQL, drops words under two characters, answers nothing for zero words, and otherwise runs one ranked query (section g, decision 6) for at most 30 rows (review).

**Detail and favourite.** Tapping a row switches the sheet to its detail view, reading `["foods", "detail", id]` and showing the row's summary at once from the list's data while the detail loads. The star sends `PUT` or `DELETE /foods/:id/favourite` optimistically: the detail and the favourites list flip at once and roll back with an error line on failure. Back returns to the results with the query, the results and the scroll position kept.

**Own food.** "Add your own food" opens `OwnFoodSheet` stacked on `FoodSheet`. Save sends `POST /foods`. On 201 the stacked sheet closes and `FoodSheet` shows the new food's detail. Edit and delete work the same way from the detail. A delete answers 204, the sheet returns to the browse view, and `["foods"]` is invalidated.

**Time zone** (review). After `me` loads, `deviceTimeZone.ts` compares the device's zone with `me.timeZone` and sends `PATCH /users/me/settings { timeZone }` when they differ, once per app start, then invalidates `["me"]` and `["targets"]`.

**Language.** Settings, Food names sends `PATCH /users/me/settings`. `["me"]` and `["foods"]` are invalidated, and every food name refetches in the new language.

**Error boundaries.** A 404 on a food closes the detail with the line "This food is no longer available." A 403 never happens from the web, because it shows no edit control on a read-only food. Network failure on a write keeps the sheet open with its error line, as the lifted form sheets do.

### The first-run gate

`TargetsGate` sits between `QueryProvider` and `AppShell`, as the scaffold design reserved:

The gate reads `["targets"]`, a key with no date in it (review), so a date change at midnight never puts the gate back into a pending state. It decides only on **whether any change exists**, and it shows the spinner only while it has no data at all. A refetch with data already held keeps rendering what it rendered, so an open sheet with typed input is never unmounted.

| ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| no data, `fetchStatus === "fetching"`                                                                             | the lifted `FullPageSpinner`                |
| data, `changes.length === 0`                                                                                      | `FirstRunTargets`, full page, no tabs       |
| data, at least one change (whatever the refetch is doing)                                                         | the shell                                   |
| no data, `fetchStatus === "paused"` (offline: TanStack's default `networkMode` pauses, it does not fail) (review) | the shell, with `OfflineStrip`              |

## g) Constraints and decisions

1. **Four pull requests, each green on its own** (section j). The backend lands first so the web PRs build against a real API.
2. **Targets as one row per dated change, with a column pair per nutrient.** The simplest shape that answers "what was in force on this day" with one indexed lookup, and that Postgres CHECKs can guard. Adding a macro is two columns. The API is keyed by nutrient, so adding one is an optional key, not a new shape.
3. **The earliest change covers every earlier date** (0.2), so a day is never without targets once the user has any. `inForce` is null only for a user with no targets.
4. **One `foods` table for every source**, so an entry, an ingredient and a favourite point at one key whatever the source. Source-specific columns are few and nullable, guarded by CHECKs.
5. **Identity is the app's UUID. Fineli's id is a join key.** A re-import never changes a UUID, never deletes a Fineli row, and reports renames for a person to read.
6. **Search: `pg_trgm` plus a documented ranking rule, no full-text search** (rewritten in review, after running it on release 18's 4,058 real names).

   **Matching.** `food_search_norm` (lower case, accents folded, every run of non-alphanumerics one space) gives `search_all` over both names, with a GIN trigram index on it. The service first runs `SELECT food_search_norm($1)` on the query, so the query and the columns are normalised by the same function. It splits the result on spaces in TypeScript, drops words shorter than two characters, removes duplicates and keeps at most eight. **Zero words answers `{ foods: [] }` with no further query**, so a query of punctuation, such as `%` or `_`, matches nothing rather than everything. Each word is then one bound parameter, `'%' || $n || '%'`. After normalisation a word holds only letters and digits, so no LIKE wildcard can reach it. **A food matches when every word occurs in `search_all`.** Retired foods and other users' own foods never match.

   **Words of one character** are dropped. The web sends nothing until the field holds two characters. A two-character word is matched by a sequential scan (trigrams need three), which takes a few milliseconds at this size.

   **Ranking, first difference wins.** `w` is the query's first word. The **head** of a name is the first word of its first part, with hyphens kept (`food_search_head`): "Kananmuna, kuoreton" has the head `kananmuna`, "Muna-kinkkuvuoka" has `muna-kinkkuvuoka`. Parts are split on ", " (a comma and a space), so the decimal comma in "rasvaa <0,5 %" never starts a part.
   1. **Match tier**, the best over the Finnish and the English name: (1) the head is `w`; (2) the head is a longer word that ends with `w`, which in Finnish is a compound whose last element is `w` ("kananmuna" is an egg, "maitorahka" is a quark); (3) the head starts with `w` ("Munakoiso", "Rahkapiirakka", "Muna-kinkkuvuoka"); (4) any word of the name is `w` or ends with it; (5) any word starts with `w`; (6) `w` occurs inside a word.
   2. The user's favourites, then the user's own foods, then the rest.
   3. Fineli `FOOD` before `DISH` before anything else.
   4. Fewer parts in the display name.
   5. Shorter display name, then the display name in the database collation, then `id`, so the order is total and stable.

   **What it does on release 18** (computed with a Python replica of the rule over the real names, and pinned as tests on a committed sample):

   | "rahka"    | 55 matches. The first 20 are all "Rahka, …" quarks. The plain quark (622, "Rahka, maitorahka, maustamaton, rasvaa <0,5 %") is 8th, behind shorter flavoured quarks. Every "Rahkapiirakka" comes after every "Rahka, …" |
   | "muna"     | 113 matches. The egg (858, "Kananmuna, kuoreton") is 1st, then the other hen's eggs. "Munakoiso" (aubergine, 362) is 12th, after every "Kananmuna" food. The rule before review put the egg 88th                       |

   **What it does not do, said plainly.** It does not put the plain variant of a food first: Fineli lists many flavoured and branded quarks, and nothing in a name says which one is "the" quark without a hand-kept list of words, which this design refuses. A fixed rule can promise that the first screen holds the right kind of food, not the right product. Daily use does not run on search: recent foods, favourites and the last amount (FR-LOG-03 to 05, step 3) carry it. **Search is for the first time a food is logged**, after which it is a recent or a favourite. Favourites rank first within their tier from day one.

   **Latency.** About 4,300 Fineli rows today, and the design is sized for 10,000 including own foods. A word of three characters or more uses the trigram index. The ranking runs over the matches only. Expected server time is under 10 ms. The gate is structural, not a benchmark (review): after seeding 10,000 rows and running `ANALYZE`, `EXPLAIN` for a three-character word shows `foods_search_all_trgm` in the plan. A loose smoke bound, a median under 150 ms over 25 queries, catches only a pathological plan. What the user feels is the network round trip, which the 150 ms debounce, request cancellation and keep-previous-results hide.

7. **The search's normalisation lives in SQL functions, and the generated columns call them**, so the index, the filter and the ranking can never disagree. The query is normalised by the same SQL function in a first round trip, and TypeScript only splits the normalised text into words (review), because each word must be its own bound parameter for the trigram index to serve it.
8. **`csv-parse` for the release, not a hand-written splitter.** The release has been plain `;` text so far, but a quoted name in a later release would break a splitter silently. `csv-parse` is maintained and has no dependencies.
9. **The release file is downloaded by hand and git-ignored** (0.10). The importer is tested on committed fixtures in the real format.
10. **Food names in the user's language come from the server**, so the assistant (step 4) and the screen get the same name. The setting is a column on `users`, read in the same query as the foods.
11. **The first-run gate is a component, not a route.** No redirect, no second mount site, no special case for deep links.
12. **The food surface is one tall sheet** with a search view and a detail view, forms stacked on it. One mount site, reused by step 3.
13. **Fineli portion labels are catalog entries keyed by unit code.** Copy stays in the catalog, and the database holds no English strings.
14. **No new rate limiter.** Every route here needs a session. Search is a cheap read.

### Rejected alternatives

| Alternative                                                              | Why it was rejected                                                                                                                                                                                            |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Targets as one row per nutrient per change (`target_ranges` child table) | A second table, an assembled read and validation that loops over rows, to buy "a new nutrient is data". Two nullable columns per new nutrient cost one migration, and the owner's wording allows columns       |
| Targets as one row per nutrient, each with its own start date            | "What was in force on day D" becomes one lookup per nutrient, and stopping tracking one needs a tombstone row                                                                                                  |
| Separate tables for Fineli foods and own foods                           | Every entry, ingredient and favourite would need two nullable keys or a polymorphic key, forever                                                                                                               |
| Postgres full-text search (`tsvector`, `finnish` config)                 | Stemming does not match partial words ("rahk"), Finnish compounds ("maitorahka") need substring matching anyway, and two configurations for two languages double the work. Trigrams answer FR-FOOD-03 directly |
| Trigram similarity ranking (`similarity()`, `<%`)                        | Fuzzy scores rank "rahkapiirakka" against "rahka" by letter overlap, not by meaning, and the order shifts with name length in ways nobody can document. FR-GAP-06's spirit is a fixed, documented rule         |
| An external search engine (Meilisearch, Typesense)                       | A second service to run on Fly for 10,000 rows Postgres serves in milliseconds                                                                                                                                 |
| Fetching from Fineli's JSON API instead of the release file              | It sits behind the same Cloudflare challenge, it is a live dependency, and section 5 asks for a repeatable import                                                                                              |
| A hand-written CSV splitter                                              | Breaks silently on the first quoted field. A maintained parser costs one small dependency                                                                                                                      |
| Committing the release                                                   | Agents cannot fetch it to commit it, the copy in git would drift from THL's page, and the importer would need an unzip dependency (0.10)                                                                       |
| A `/welcome` route for the first run, with redirects                     | A redirect from every route, a redirect back, a loop guard and lost deep links, to show one screen                                                                                                             |
| Food search as its own page or a fifth tab                               | The four-tab shell is settled. A page means step 3 opens it from a sheet or navigates away from the Day mid-log                                                                                                |
| Base UI `Combobox` or `Autocomplete` for search                          | A floating list on a phone is what the lessons warn against. A sheet with an in-flow list is their recommendation                                                                                              |
| The search, the detail and the forms as views of one sheet               | The forms then lose the lifted form-sheet contract (dirty refusal, keyboard handling) or re-implement it per view                                                                                              |
| Storing English portion labels in the database                           | UI copy outside the catalog, and a translation the catalog cannot see                                                                                                                                          |

## h) Open questions and risks

1. **Prefill a later targets change with the user's own numbers?** (0.1, review)
   > **Assumption:** no. Every targets form starts empty, by the orchestrator's ruling on FR-TGT-04, and the targets in force show as text. One-line flip once Artur accepts the proposed wording: `TargetsSheet` sets its initial values from the in-force change it already reads.
2. **Remove a dated change** (not asked for, 0.4).
   > **Assumption:** allowed, never the last one. Flip: drop one route, one service, one button.
3. **Retire, never delete, a Fineli food that leaves a release** (not asked for, 0.6).
   > **Assumption:** retire. No sensible flip.
4. **The import's retire guard at 10 %** (not asked for).
   > **Assumption:** on. Flip: delete the guard and its flag.
5. **Food-name language default** (0.5).
   > **Assumption:** Finnish. Flip: the column default.
6. **Is `(arc)` in a Fineli name "archived"?**
   > **Assumption:** yes, such foods are imported retired. Flip: import them live, one line in the importer.
7. **A user's today from a stored zone, written by the device** (0.12, review).
   > **Assumption:** yes, starting from `Europe/Helsinki`. Flip: every read that needs today takes a date parameter.
8. **Delete account on the first-run screen** (0.9, review).
   > **Assumption:** yes, with Sign out. Flip: remove one button.
9. **Does the current release keep release 18's format?**
   > **Assumption:** yes, with the importer tolerant of encoding, line ends and quoting. The first real run is the check, and it fails loudly on a missing file or column.

**Risks:**

- **Fineli facts rest on release 18 (2015).** Mitigation: header-based reading, encoding detection, the strict missing-file and missing-column errors, the retire guard, the rename report, and a `TODO.md` item to confirm on the first real download.
- **Agents cannot download the release** (Cloudflare challenge). Step 3's hand-over needs real foods locally. Artur downloads the zip once and unzips it into `apps/backend/data/fineli/` before testing. The orchestrator says so at the hand-over.
- **`pg_trgm` and `unaccent` on Fly's Postgres image.** Both are contrib extensions that `flyio/postgres-flex` ships, and the app's database user owns the database there. The Fly runbook gains a check (`SELECT * FROM pg_available_extensions WHERE name IN ('pg_trgm', 'unaccent')`). If either is missing, the release command fails before traffic moves, so nothing breaks silently.
- **The web scaffold is in flight in `/home/user/hovi-web`.** `packages/types/src/auth.ts` (`MeSchema`) and `apps/web` files named in section b (`(app)/layout.tsx`, `queryKeys.ts`, `Icon.tsx`, `BottomSheet.tsx`, `messages/en.json`) are being written there now. PR 2a only adds a field to `MeSchema`. PRs 2c and 2d start only after scaffold PRs 2 and 3 merge, from a fresh `origin/master`.
- **A sheet at a fixed tall height with the iOS keyboard.** The field is pinned at the top and the list scrolls, so the keyboard only covers list rows, but `VirtualKeyboardProvider` may still scroll the body. ui-validator emulates the keyboard through `visualViewport` on WebKit, and the real check on Artur's iPhone joins the existing `TODO.md` item.
- **Drizzle `numeric` in number mode.** If 0.45 lacks it, values arrive as strings. The engineer converts in one mapper per table.
- **Search latency on CI** (review). The gate is the `EXPLAIN` check, which does not depend on the runner's speed. The 150 ms smoke bound is about fifteen times the expected cost.
- **Search quality on the current release** (review). The ranking was measured on release 18 only. The 2b manual check repeats the pinned queries on the release 18 mirror after a real import run, and the `TODO.md` item repeats them on the current release when Artur downloads it. A worse result there is tuned in the rule and re-pinned, never patched with a word list.
- **The device writes the time zone** (review). A traveller's zone follows the device at the next app start, so "today" can lag by one app start. A zone that `Intl` on the server does not know is refused, and a stored one that becomes unknown falls back to `Europe/Helsinki` with a log line.

- Search always matches both languages. Veto cost: one condition.
- A Fineli food that leaves a release is retired, never deleted. Veto cost: not advisable.
- A Fineli food missing a value is left out. Veto cost: zeros in the catalogue.

- Own food value caps: 1000 kcal and 100 g per 100 g. Portion cap 5000 g. Barcode 8 to 14 digits, no check digit test. Veto cost: Zod and CHECK values.
- A user's own food has one name, shown in either language. Veto cost: a second name field.
- Food search sits in a tall sheet opened from the Day tab. Veto cost: a page and a link.

## Deviations from the design (PR 2a, backend engineer)

Each is the smallest sound choice where the doc was silent or could not be built as written.

1. **Function bodies are schema-qualified.** `food_search_norm` and `food_search_head` call `public.f_unaccent`, and the functions are created as `public.*`. A restore that sets an empty `search_path` (as `pg_dump` output does) recomputes the generated columns, and an unqualified call would fail there.
2. **`IsoDateSchema` also refuses year 0000.** Zod's `z.iso.date()` accepts `0000-01-01`, which Postgres has no year for, so the route answered 500. It now answers 400 `invalid_date`.
3. **Search patterns are bound whole** (review round 2): each `%word%`, `%w`, `w%`, `%w ` and `% w%` is built in TypeScript and bound as one parameter, not concatenated in SQL.
4. **The Fly runbook's extension check lands in 2a**, not 2b, because migration 0001 ships here and a deploy of 2a needs both extensions.
5. **`foods.md` has no "The Fineli import" heading yet**, and the link map has no row for it. The importer does not exist until 2b, which adds both.
6. **`contextFor(req)` lives in `apps/backend/src/lib/requestContext.ts`.** The doc named the function but no file. It is route-side, because it reads `req`. Services never import Express.
7. **The ranking sample takes each pinned query's first 40 on release 18, not 30**, so a collation difference in the last tie-break cannot pull an unsampled food into a first 30. It holds 249 foods. Every assertion was run on UTF-8 databases with ICU `en-US` (as CI sorts) and with `C.utf8`.
8. **Test users are inserted directly** (`src/__tests__/support/apiUser.ts`) with a signed access token. Signing up through the route hits the sign-up rate limit after ten accounts.
9. **For PR 2b: run `VACUUM ANALYZE foods` after an import.** A bulk insert fills the GIN index's pending list, and until a vacuum the planner prices `foods_search_all_trgm` above a full scan (measured: a seq scan after `ANALYZE` alone, the index after `VACUUM ANALYZE`). Autovacuum gets there eventually, but the import should not leave search on a full scan until it does.
10. **The "old rule" check** (run once on the sample): counting parts on every comma, and also splitting the head on every comma, fails the "rahka" case only. The "muna" case is guarded by the tier order instead: swapping tiers 2 and 3 fails "muna", "kaura" and "kana".
11. **`invalid_time_zone` has a backend message** ("That is not a time zone this server knows."), because `ERROR_MESSAGES` needs one for every code. The web shows no copy for it.

## Deviations from the design (PR 2b, backend engineer)

1. **The fixtures are real release 18 rows, not invented values**, by the orchestrator's brief. 18 foods in release A, credited under CC BY 4.0 in `fixtures/README.md`. One row is invented: `858;PORTTBL;55,00`, because release 18 has no unit outside the kept ten. Release B "brings back" a food by dropping `(arc)` from 572's name, and a test runs A, B, A to bring back the food B dropped.
2. **A fifth file, `cli.ts`**: argument parsing, the run with `VACUUM ANALYZE foods`, and exit codes 0 (done), 1 (unreadable release or tripped guard), 2 (bad arguments). `index.ts` is only the entry point, so tests drive the command without a child process.
3. **The command builds its own pool from `DATABASE_URL` alone**, without `db/index.ts`. That module parses the app's whole env (JWT and relay secrets) and sets an 8 s `statement_timeout`, which a full import transaction on a small machine could hit.
4. **A portion weight outside 0 to 5000 g is left out and counted.** Release 18 has a whole turkey (752) whose medium and large pieces weigh 6000 g and 8000 g, which the `food_portions_grams_positive` CHECK refuses.
5. **A retired food keeps its Fineli measures.** Measures are removed only from foods in the release, so whatever points at a retired food still reads its portions.
6. **A known food that a release leaves out** (for a missing or out-of-range value) is retired like a food absent from the release, rather than kept live with old figures. The report counts the two cases apart and names each food of the second (fix cycle 1), and the feature doc says so.
7. **Windows-1252 is decoded by hand for 0x80 to 0x9F.** Node 22's `TextDecoder("windows-1252")` decodes it as Latin-1 and turns those bytes into control characters. Release 18 has none in its name files, a later release may.
8. **Files are found whatever the case of their names, and a FOODID listed twice in `food.csv` stops the import.**
9. **An advisory lock (`pg_advisory_xact_lock(hashtext('fineli_import'))`) serialises imports.**
10. **Values are rounded to their columns' scale before they are compared**, so a second run is unchanged: macros to three decimals, grams to one. On release 18 that touches three foods (pear fat 0.0875 g becomes 0.088 g) and eight measures (6.75 g becomes 6.8 g, 0.25 g becomes 0.3 g). Every other value matched the source exactly, checked for all 4,050 foods and 19,190 measures.
11. **The report ends with the CC BY credit and the no-endorsement sentence**, so whoever runs the import sees it.
12. **An own food name needs a word of two letters or digits, not one character** (`food_name_not_searchable`). Search drops words under two characters (`MIN_WORD_LENGTH`), so a name such as "A" or "A B" could never be found. The shared schema approximates the rule with `[\p{L}\p{Nd}]{2,}` on the NFC name. The service decides with the search's own `searchWords`, so an MCP caller that bypasses the schema is refused too.
13. **The collation pin is `fi-x-icu`**, checked present in the agent container's Postgres 16 (Ubuntu, ICU). CI's `postgres:16` is the Debian PGDG build with ICU, and Fly Postgres images are built from it; the new tests fail in CI if it is absent, and the Fly runbook checks for it. It also orders portion names in a food's detail.
14. **Migration 0001 is edited in place** (fix cycle 1). Its comment now says which calls are schema-qualified (the extension and the search functions) and which resolve through `pg_catalog` (`lower`, `btrim`, `regexp_replace`, `split_part`). It also gains the `fi-x-icu` guard (deviation 18). Drizzle's migrator compares only `created_at` with each migration's `folderMillis` and never reads an applied migration's hash back, and nothing is deployed, so an edit reaches every new database and breaks none.
15. **The Fly runbook checks the app role's `CREATE` on its database and the `fi-x-icu` collation**, beside the extension check.

### Fix cycle 1 (review and validator findings, PR 2b)

16. **The report partitions the foods read.** Added, changed, unchanged, back, newly "(arc)" and left out add up to the number read, and a sum line says so. Retirements of catalogue foods sit apart, because a food absent from the release is not a food read. The count of "(arc)" foods is a sentence, not a line of the partition. Adding or dropping "(arc)" is not listed as a rename.
17. **The report prints before `VACUUM ANALYZE`.** A database failure during the import says "Fineli import failed. Most likely nothing was written." with exit code 1, and points to a dry run, because a connection lost during COMMIT leaves the outcome unknown (fix cycle 2). A failed refresh after a written import says so with exit code 3, so the person knows the catalogue changed. The entry point swallows idle pool errors, so no failure ends in a stack trace.
18. **Migration 0001 refuses a server without `fi-x-icu`**, in a `DO` block beside the encoding guard, so a server built without ICU fails the first deploy instead of answering 500 on every food read. The test runs the guard's own statement from the migration file, as written and with a collation name no server has, because every server the tests run on has ICU.
19. **`component_value.csv` keeps only the four needed components while it parses** (`on_record` in csv-parse). Peak memory on the full release 18, dry run over a full catalogue: 236 MB before, 140 MB after. A first, writing run peaks at 159 MB.
20. **A damaged UTF-8 file is refused.** A file that fails strict UTF-8 but holds more than ten valid UTF-8 multibyte sequences stops the import, naming the file and its first bad line. Release 18's five Windows-1252 files hold no such sequence, and a UTF-8 name file holds about a thousand, so ten separates them with a wide margin both ways.
21. **A rename guard**, shaped like the retire guard: more than 5 % of live Fineli foods renamed, and more than ten, stops the import before writing unless `--allow-rename` is given. No second real release is reachable from here to count real renames between releases. The threshold rests on two figures instead. A mis-decoded name file renames every Finnish name with a non-ASCII letter, which is 1,275 of 4,058 (31 %) in release 18, six times the threshold. **Assumption, unverified:** THL's editorial renames between releases stay well under 5 % (about 200 foods). Release 18 dates from 2015 and the current release is about ten years newer, so the real count may be larger. The first real import records it, and the share is revisited then. The floor of ten keeps a small catalogue, such as the test fixtures, from tripping on one rename. The message shows three renames, so a person sees garbled letters at once. The first real import of a current release should record its rename count in the `TODO.md` item that confirms the release, and the share be revisited if it is close.
22. **A header that parses to one field** says the file does not look semicolon-separated, instead of naming a missing column.
